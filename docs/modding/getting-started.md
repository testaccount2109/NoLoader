# Create your first NoLoader extension

This guide takes you from an empty project folder to an extension running in NoRisk Client. NoLoader extensions customize the **launcher**. They are not Minecraft JAR mods and do not run inside a Minecraft game. They can add launcher pages and widgets, read launcher data through the API, and request specific desktop capabilities.

## Before you begin

To build an extension you need:

- A NoLoader-enabled NoRisk Client installation. Open **NoLoader** in the launcher to confirm it is available.
- Node.js 18 or newer and Yarn Classic 1.22 for building the SDK examples.
- A text editor and basic TypeScript or JavaScript knowledge.

You do not need Rust or the full launcher source to build an extension. The ready-to-use SDK is in this repository under `sdk/`.

## Build and install an example first

From the repository root, install dependencies and build the small Hello example:

```powershell
yarn install --frozen-lockfile
yarn sdk:hello-mod:build
```

In NoRisk Client, open **NoLoader → Open extensions folder**. Copy the whole `sdk/hello-mod` folder there, including `noloader.mod.json`, `styles.css`, and the generated `dist` folder. Return to NoLoader, refresh the list, and enable **Hello NoLoader**. The extension adds a page and a navigation item. If you edit its files later, rebuild and refresh NoLoader to load the changes.

The app-data folder is normally `%APPDATA%\gg.norisk.NoRiskClientLauncherV3\NoLoader\mods` on Windows. Prefer the button in the launcher because it opens the correct folder for that installation.

## Make your own extension

Copy `sdk/hello-mod` to a new folder and give the extension a permanent, unique ID. Use a reverse-domain style ID you control, for example `dev.alex.example`. Keep the ID stable after publishing: saved data and extension settings are associated with it.

The important files are:

```text
my-extension/
├── noloader.mod.json    # Identity, compatibility, entry points, permissions
├── package.json         # Build command and SDK workspace reference
├── tsconfig.json        # TypeScript settings for the Web Worker
├── vite.config.ts       # Builds one self-contained ES module
├── src/
│   └── index.ts         # Exports activate(api)
├── styles.css           # Optional extension styles
└── dist/
    └── index.js         # Generated by the build; this is what NoLoader loads
```

Change the `name`, `id`, `version`, description, author, and permissions in `noloader.mod.json`. Set `entrypoints.frontend` to the generated JavaScript file. Keep dependencies bundled into this single entry point; the worker does not have a Node.js `require` function and cannot load files from npm at runtime.

The example imports compile-time API types from `../../types/no-loader`, which works when the project lives in this repository's `sdk/` folder. If you build elsewhere, copy `sdk/types/no-loader.d.ts` into your project and update the type import path. These declarations are used by TypeScript only and are removed from the built JavaScript.

### A minimal extension

The entry point must export a named `activate` function. A standard-trust extension receives the documented API in a dedicated worker, registers UI, and may return a cleanup function:

```ts
import type { NoLoaderApi, NoLoaderActivation } from "../../types/no-loader";

export function activate(api: NoLoaderApi): NoLoaderActivation {
  const removePage = api.registerPage({
    id: "welcome",
    title: "My first extension",
    content: [
      { type: "heading", level: 1, text: "Hello!" },
      { type: "text", text: "This page is rendered by NoRisk Client." },
      { type: "button", id: "hello", label: "Say hello", action: "hello" },
    ],
  });

  const removeNavigation = api.registerNavigationItem({
    id: "welcome",
    label: "My extension",
    pageId: "welcome",
    icon: "sparkles",
  });

  const removeAction = api.onAction((action) => {
    if (action === "hello") {
      void api.notifications.show({ title: "Hello", body: "Your extension is running." });
    }
  });

  return () => {
    removeAction();
    removeNavigation();
    removePage();
  };
}
```

This example needs the `ui.pages`, `ui.navigation`, and `launcher.notifications` permissions. Add them to the manifest before building. Every registration returns a cleanup function; call it when the extension stops so the host can remove its UI and handlers promptly.

NoLoader can also mark an extension as **high trust** when it is imported. High-trust extensions run directly in the launcher webview and bypass the standard worker/API permission boundary. Only choose that mode for code you own or have fully audited. A normal extension should use standard trust and request only the manifest permissions it needs.

### Build your extension

Give your extension a build script in its `package.json`. The SDK examples use Vite and produce `dist/index.js`:

```json
{
  "scripts": {
    "typecheck": "tsc --noEmit",
    "build": "yarn typecheck && vite build"
  },
  "devDependencies": {
    "typescript": "5.6.3",
    "vite": "6.3.5"
  }
}
```

Build from the repository root with the matching workspace command, or run the example's build script from its folder. After each build, copy the generated `dist` folder into the installed extension folder and refresh NoLoader. NoLoader reads the files on startup or refresh; it does not watch your source files.

## Understand compatibility

Two manifest fields describe different kinds of compatibility:

- `apiVersion` is the NoLoader extension API version the code uses. Current NoLoader builds support API versions 1 through 6. Choose the lowest API version that contains every method your code calls.
- `launcherVersions` lists exact NoLoader host versions. `launcherVersionRange` is an optional space-separated SemVer range for host versions where the extension is known to work. When present, the range takes precedence over the exact list. For example, `">=0.6.30-noloader.4 <0.6.30-noloader.5"` supports that host release only. Expand the range when you have checked a later launcher version and know your extension remains compatible.

The displayed product release (for example, **NoLoader Launcher 1.0.11**) is separate from the extension host version returned to extensions (currently `0.6.30-noloader.4`). Use the host version in your compatibility declaration. A compatibility range is an author statement: NoLoader cannot prove that an unrelated launcher change has no effect on your code.

## Add an update feed

An update feed is a small HTTPS JSON file you host. For example:

```json
{
  "id": "dev.alex.example",
  "version": "1.1.0",
  "downloadUrl": "https://example.org/releases/example-1.1.0.zip",
  "changelogUrl": "https://example.org/releases/1.1.0.html"
}
```

Add the feed URL to the manifest:

```json
"updates": {
  "manifestUrl": "https://example.org/releases/latest.json",
  "autoInstall": false
}
```

With `autoInstall` omitted or `false`, NoLoader reports a newer version and offers the feed's download and changelog links. Set it to `true` only if you intend NoLoader to install packages without asking each time. Then `downloadUrl` must point to a ZIP with `noloader.mod.json` at the ZIP root. The ZIP manifest must contain the same `id` and `version` as the feed. NoLoader checks that identity, stages the package, rejects unsafe paths and symbolic links, and replaces the installed folder after validation. Automatic checks happen when NoLoader starts or the user refreshes the mod manager, including for an extension whose current manifest is incompatible with the running host. This lets an author publish a compatible build that can replace the outdated copy.

The package is executable extension code. HTTPS and the ID/version checks do not prove who authored it or make it safe; publish updates only from infrastructure you control and review the built ZIP before publishing it.

See the full [manifest reference](manifest.md) for all fields and limits.

## Prepare a release

Build the extension, then create a ZIP that contains the **contents** of its installed folder at the archive root. Include the manifest, generated `dist/index.js`, and any declared stylesheet or runtime assets. Do not wrap these files in an extra enclosing directory. Test by installing that exact ZIP into a clean NoLoader profile before publishing its URL.

Increase the manifest's SemVer `version` on each release. Publish the ZIP first, then publish the JSON feed with the matching ID and version. Keep the ID and host version range correct. For more details, read [API reference](api-reference.md), [permissions](permissions.md), [lifecycle](lifecycle.md), and [security](security.md).

## Troubleshooting

- **The mod is not listed:** confirm its folder is inside the directory opened by **Open extensions folder**, and that `noloader.mod.json` is directly inside the folder.
- **Manifest is invalid:** open the NoLoader manager and read the mod's error detail. Field names are case-sensitive; the parser rejects unknown fields and malformed JSON.
- **Incompatible:** compare the running host version with `apiVersion`, `launcherVersions`, and `launcherVersionRange`. Widen a range only after checking the code against that version.
- **A button does nothing:** confirm the action string matches the one checked in `api.onAction`, and that the needed permission is listed in the manifest.
- **The mod fails to load after editing:** rebuild the bundle, confirm `entrypoints.frontend` points to it, then refresh the manager. Safe mode stops all extensions while preserving their enabled settings.
- **An update failed:** verify that all URLs use HTTPS, the feed ID and version match the package manifest, and the ZIP has the manifest at its root.
